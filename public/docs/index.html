Binding format

The anchors.json file downloaded from the Anchor page contains a single top-level key anchor_bindings, which is an array of entries. Each entry corresponds to one timestamp authority.

RFC 3161 binding (one entry):

{
  "type": "rfc3161-tst",
  "anchored_hash": "sha256:<64 hex chars>",
  "log_origin": "http://timestamp.digicert.com",
  "proof": "<base64 DER TimeStampToken>",
  "policy_oid": "2.16.840.1.114412.7.1",
  "serial": "<hex>",
  "gen_time": "2026-07-02T22:00:00.000Z",
  "signer_cert_chain_b64": ["<base64 DER leaf cert>", "..."]
}

OpenTimestamps binding (one entry):

{
  "type": "opentimestamps",
  "anchored_hash": "sha256:<64 hex chars>",
  "log_origin": "bitcoin",
  "proof": "<base64 .ots bytes>"
}

When an OpenChainGraph artifact is anchored, the same entries appear in the anchor_bindings array at the top level of the re-emitted artifact. The execution_hash and all other fields are untouched (anchor data sits outside the hash scope per OCG section 20).

Verify with openssl

Extract the DER from an anchors.json binding and verify it independently of this site: 

# Extract proof DER (requires python3 or similar base64 tool)
python3 -c "
import json, base64
b = json.load(open('anchors.json'))['anchor_bindings'][0]
open('tst.der','wb').write(base64.b64decode(b['proof']))
"

# Verify (adjust -CAfile to the relevant pinned root)
openssl ts -verify \
  -digest <sha256-hex> \
  -in tst.der \
  -CAfile digicert-trusted-root-g4.pem

The -digest value is the anchored_hash field with the sha256: prefix removed. Root PEM files are in the repo.

Timestamp authorities

The Anchor page offers six choices:

AuthorityHow it reaches the TSANotes
Sigstore TSA Browser-direct (CORS open) OpenSSF public-good; accepts JSON as well as DER
DigiCert Relay at /relay/digicert Commercial CA; AATL root; no use restrictions
Sectigo Relay at /relay/sectigo Commercial CA; relay enforces 15-second pacing
FreeTSA Relay at /relay/freetsa Community TSA (one person in Bavaria); pair with a CA for reliability
GitHub TSA Browser-direct (CORS open) HSM-backed; undocumented for third-party use
OpenTimestamps Browser-direct to OTS calendars Bitcoin-anchored; proof is pending for several hours after stamping

The relay is a stateless Cloudflare Worker that pipes DER bytes verbatim. It parses nothing, stores nothing, and logs no request bodies. Rate limit: 4 requests per minute per IP.

Pinned roots

Sigstore and GitHub roots are not in OS trust stores, so this site pins them. The Verify page uses these same pinned roots for offline-capable verification. The roots are committed in public/vendor/roots/ and documented in ROOTS.md. CI warns 90 days before any pinned cert expires.

OpenChainGraph support

Drop an OCG artifact on the Anchor page and the tool:

  1. Reads the execution_hash field (no re-hash of the raw file).
  2. Optionally verifies the execution hash against the artifact body (section 4 recompute).
  3. Anchors the execution hash at the selected timestamp authorities.
  4. Offers a download of the artifact with anchor_bindings appended per OCG v0.7 section 20.

The Verify page runs all three OCG verification paths on dropped artifacts: section 4 (execution hash), section 16 (eddsa-jcs-2022 signature), and section 18 (Groth16-BN254 compute proof), all client-side using the vendored OCG verifier library.

Anchor the receipt on your own chain

You can record a receipt hash on Base, Optimism or Solana, with your own wallet. Your wallet signs and pays. Anchor Suite never sees a key and never submits a transaction. This adds a ledger-ordering record next to your RFC 3161 and OpenTimestamps timestamps; it does not replace them. Use the execution_hash of the finished receipt as the 32-byte value, or a Merkle root that includes a nonce leaf, so nobody can guess and stamp it before you do.

Base and Optimism: EAS timestamp(bytes32)

Both chains carry the Ethereum Attestation Service as a predeploy at 0x4200000000000000000000000000000000000021, the same address on Base mainnet and Base Sepolia. Source: Base contract addresses; for Optimism see the OP Stack smart contracts overview. We also read that address live: getTimestamp(bytes32) on it returned the expected block times for the first EAS timestamp on Base Sepolia and Base mainnet, so on those two networks the address matches a real call, not only the docs. We have not read the Optimism address ourselves. Check it again on the day you run it. The functions are timestamp(bytes32 data) returns (uint64) and getTimestamp(bytes32 data) returns (uint64), from IEAS.sol.

The read was checked against the first EAS timestamps on Base Sepolia and Base mainnet. The write step is shown from real third-party transactions and a simulated call to the contract; Anchor Suite has not sent a transaction itself, and your wallet signs and pays. Illustrative sample with placeholders only, not output from a real transaction; fill in your own values:

# Illustrative sample, placeholders only
# Record (your wallet signs and pays)
export HASH=0x<64 hex chars of your execution_hash>
cast send 0x4200000000000000000000000000000000000021 \
  "timestamp(bytes32)" $HASH \
  --rpc-url YOUR_RPC --private-key "$YOUR_KEY_ENV"

# Read back; ask for the finalized block
cast call 0x4200000000000000000000000000000000000021 \
  "getTimestamp(bytes32)(uint64)" $HASH \
  --rpc-url YOUR_RPC --block finalized

A non-zero result is the block time of the earliest recorded stamp of that hash. If the hash was stamped before, the call reverts instead of overwriting.

Solana: memo

Send a transaction whose Memo-program instruction data is the hash string, signed by your own account. Then record it as a solana-memo binding (SPEC section 20.4).

Where the result goes in a receipt

Illustrative values, truncated on purpose. Hand-written, not output from a real transaction:

{
  "anchor_bindings": [
    {
      "type": "solana-memo",
      "cluster": "mainnet-beta",
      "signature": "<base58 signature, truncated>",
      "slot": 123456789,
      "commitment": "finalized",
      "signer": "<base58 pubkey, truncated>",
      "anchored_hash": "sha256:<64 hex chars, truncated>"
    }
  ]
}

There is no binding type for an EAS timestamp on Base or Optimism yet. Until one exists, keep the chain name, contract, block number and transaction hash next to the receipt in your own records.

What this does and does not show

On Base, Optimism or Solana, a chain anchor is ledger-ordering evidence: the chain records this hash by block N. It is not an RFC 3161 timestamp and not a qualified timestamp, and checking it needs an RPC endpoint that you choose; that RPC operator sees the hash you query. Read at the chain's finalized tag, and treat anything less as pending. Do not read an EAS timestamp as showing who recorded the hash. The EAS contract stores only a time against the hash, and the first stamp of a hash is the one that counts. Anyone could have written the same hash. A Base record depends on Base's sequencer and RPC operators and is not independent of them. This is technical documentation, not legal advice.

x402 payments

Record the receipt hash in a follow-up transaction on Base, Optimism or Solana, after you have the finished receipt. Optionally, timestamp a salted digest of the mandate before paying, with an RFC 3161 or OpenTimestamps timestamp.

Verifying

Anchor Suite verifies the Solana memo leg today. A Base check is not built yet. For a chain other than Base, Optimism or Solana, ask us.

Security model

Post Oak Labs is not a timestamp authority and never stores your hash. The relay Worker forwards bytes verbatim; the authorities listed in your receipt are the issuers of the evidence.

Content Security Policy: script-src 'self', connect-src exact allowlist, require-trusted-types-for 'script'. No analytics, no third-party scripts, no CDNs.

Source code and vendored libraries are published at github.com/PostOakLabs/anchor-suite.
